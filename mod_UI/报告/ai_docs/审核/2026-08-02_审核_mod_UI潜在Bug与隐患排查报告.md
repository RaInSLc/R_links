# mod_UI 项目潜在 Bug 与隐患排查报告

**文档版本**: 1.0.0  
**排查日期**: 2026-08-02  
**排查对象**: `mod_UI` (前端 React / 后端 Tauri Rust)  
**文档类型**: 代码排查与审核报告  

---

## 1. 排查背景与概述

为了确保 `mod_UI` (R 包安装命令工作台) 在生产环境及高强度并发使用下的绝对稳定，我们对前端 React 逻辑（`src/`）、Tauri Rust 后端 IPC 指令（`src-tauri/src/`）以及组件交互、异步状态控制进行了全方位的二轮 Bug 与隐患深度排查。

本次排查共发现 **6 项逻辑缺陷与潜在隐患**（包含 1 项异步竞态 Bug、1 项多生态功能断层 Bug、1 项 UI 坐标计算溢出 Bug，以及 3 项边界容错隐患）。本报告详细记录了各 Bug 的触发条件、代码位置、潜在后果及具体修复方案。

---

## 2. 核心 Bug 与隐患清单

### Bug 1: `useSearch.ts` 中 `startBinarySearch` 的状态污染与竞态 Bug (P0 紧急)

- **代码位置**: `mod_UI/src/useSearch.ts` (`startBinarySearch` 函数 L154-L178)
- **现象描述**:
  在 `startSearch` 中，系统会严格校验 `if (clean.runId !== activeSearchRunId.current) return;` 并在 `finally` 中判断 `if (runId === activeSearchRunId.current)` 再重置检索状态。然而，在 `startBinarySearch` 中，缺失了此项关键的比对逻辑：
  ```typescript
  // 当前存在缺陷的代码逻辑
  try {
    const response = await invoke<SearchResponse>("start_binary_search", { runId, input, settings, mirror });
    const clean = sanitizeSearchResponse(response);
    setResults(clean.results); // ❌ 未校验 runId 是否依然活跃，直接覆盖全局结果
    setLogs(clean.logs);
    setStatus("R 二进制包检索完成");
  } catch (error) {
    setStatus(`R 二进制包检索失败: ${formatError(error)}`);
  } finally {
    // ❌ 无条件清空 activeSearchRunId，即使已有新检索任务在运行
    setSearchDuration(Date.now() - searchStartTime.current);
    setSearching(false);
    setPaused(false);
    searchingRef.current = false;
    activeSearchRunId.current = 0;
  }
  ```
- **触发条件**: 当用户发起“R 二进制包检索”后，在响应返回前点击了“停止”或快速发起了新的普通检索任务。
- **后果**: 延迟返回的二进制检索响应会强制覆盖新任务的结果与日志，并将新任务的 `activeSearchRunId` 归零，破坏 UI 的运行状态指示器。
- **修复方案**:
  在 `startBinarySearch` 的 `try` 块赋值前及 `finally` 状态重置前，统一加上 `if (runId === activeSearchRunId.current)` 防护条件。

### Bug 2: `Pip` 与 `Conda` 多生态脚本生成引擎断层 (P0 紧急)

- **代码位置**: 
  - 前端: `mod_UI/src/WorkspaceView.tsx` (生态选择器 `onEcosystemChange`)
  - 后端: `mod_UI/src-tauri/src/lib.rs` / `logic.rs` (`generate_script` 指令)
- **现象描述**:
  前端在 `WorkspaceView` 中提供了切换 `Pip` 和 `Conda` 包生态的 Tab 选项，但在向 Rust 后端调用 `generate_script` 生成最终安装脚本时，只传递了 `input`、`options` 和 `results`，后端 `logic::generate_script_with_rules` 缺乏接收 `ecosystem` 参数的分支处理。
- **触发条件**: 用户在 UI 中将包生态切换为 `Pip` 或 `Conda` 后点击“生成脚本”。
- **后果**: 生成的脚本仍然是 R 语言的 `install.packages()` 或 `BiocManager::install()` 指令，与 Pip/Conda 生态严重脱节，无法生成真正的 `pip install` 或 `conda install` 命令。
- **修复方案**:
  1. 向 Tauri `generate_script` 命令扩展 `ecosystem: String` 参数。
  2. 在 `logic.rs` 中新增 Pip (`pip install <pkg>==<ver> -i <index>`) 及 Conda (`conda install -c <channel> <pkg>=<ver>`) 脚本生成器逻辑。

### Bug 3: `ReportView.tsx` 依赖图谱 SVG 纵坐标 Y 溢出与节点裁剪 (P1 高)

- **代码位置**: `mod_UI/src/ReportView.tsx` (`DependencyGraphView` 组件 L110-L145)
- **现象描述**:
  在计算 SVG 依赖节点的纵坐标 `y` 时：
  ```typescript
  const nodeSpacing = 48;
  const svgHeight = Math.max(450, maxNodesInLevel * nodeSpacing + 60);
  // ...
  const y = count === 1
    ? svgHeight / 2
    : (svgHeight - (count - 1) * nodeSpacing) / 2 + index * nodeSpacing;
  ```
  当某一层节点数较多（例如 10 个以上节点）时，由于顶部计算居中偏移 `(svgHeight - (count - 1) * nodeSpacing) / 2`，在某些边界下会导致起始节点 `y` 坐标出现极小值或负数，使顶部/底部节点超出 SVG 视窗。
- **触发条件**: 输入包含大量同层依赖包的复合分析任务（如 `Seurat` 或 `DESeq2` 依赖图谱）。
- **后果**: SVG 图谱顶端和底部的节点被裁剪在视窗之外，用户无法在图谱中查看或点击这些节点。
- **修复方案**:
  增大纵向 Padding 预留，并确保 `svgHeight` 的最小计算基准能够安全容纳所有节点的渲染高：
  ```typescript
  const svgHeight = Math.max(480, maxNodesInLevel * nodeSpacing + 120);
  const startY = 60;
  const y = count === 1 ? svgHeight / 2 : startY + index * nodeSpacing;
  ```

### Bug 4: 离线缓存反馈 (`rate_cache_result`) 的严格匹配导致评分失败 (P1 高)

- **代码位置**: `mod_UI/src-tauri/src/lib.rs` (`rate_cache_result` 与 `cache_entry_matches_result`)
- **现象描述**:
  后端在处理缓存点赞/踩反馈时，要求传入的参数与缓存条目进行 100% 严格比对：
  ```rust
  fn cache_entry_matches_result(
      entry: &models::PackageCacheEntry,
      source: &str,
      version: &str,
      repository: &str,
      real_name: &str,
  ) -> bool {
      entry.source == source
          && entry.version == version
          && entry.repository == repository
          && entry.real_name.eq_ignore_ascii_case(real_name)
  }
  ```
  但在前端从历史记录或离线匹配生成 `SearchResult` 时，`repository` 或 `source` 可能因镜像规范化被处理为带/不带尾部斜杠（例如 `https://cloud.r-project.org` 与 `https://cloud.r-project.org/`），或者 `repository` 为空字符串。
- **触发条件**: 用户对带有规范化差异或离线导出的缓存记录点击赞/踩。
- **后果**: 比对失败，后端抛出 `"当前结果与缓存记录不一致，已跳过反馈"`，使用户的反馈操作无法成功记录。
- **修复方案**:
  在 `cache_entry_matches_result` 中使用 URL 规范化比较（忽略结尾 `/`），并允许 `repository` 在 CRAN 等标准来源下进行松散匹配。

### Bug 5: `WorkspaceView.tsx` 字母按排序 (`sortInputAlphabetical`) 破坏注释绑定隐患 (P2 中)

- **代码位置**: `mod_UI/src/WorkspaceView.tsx` (`sortInputAlphabetical` 函数 L137-L150)
- **现象描述**:
  按字母排序函数将注释行独立抽出并记录其原始行索引 `idx`，对非注释包名行排序后再按原 `idx` 插入：
  ```typescript
  comments.forEach((c) => active.splice(c.idx, 0, c.line));
  ```
  在按字母重新排列包名后，原先紧贴在某包名下方或上方的说明注释（例如 `# 生信单细胞分析核心包`）会被插到按字母新排上来的完全无关的包上。
- **触发条件**: 用户在输入列表中书写了行内或紧跟包名的说明注释，并点击了“字母排序”。
- **后果**: 注释与包名的对应关系被彻底打乱，造成语义混乱。
- **修复方案**:
  重构排序逻辑，将紧贴在包名上方的注释与该包名绑定为一个“包名块 (Package Block)”，以包名作为 Key 进行整体排序。

### Bug 6: 缓存批量导入 (`import_package_cache`) 缺少单条容错 (P2 中)

- **代码位置**: `mod_UI/src-tauri/src/storage.rs` (`import_cache` 函数)
- **现象描述**:
  缓存导入函数采用全量反序列化方案：
  ```rust
  let imported: HashMap<String, PackageCacheEntry> = serde_json::from_str(content)?;
  ```
  若导入的 JSON 文件中有一条记录包含了旧版本不兼容的类型或损坏的字段，整个 JSON 解析将立即报错中断。
- **触发条件**: 导入由旧版本导出或经过人工编辑的缓存 JSON 文件。
- **后果**: 即使 99% 的记录有效，整批导入也会完全失败。
- **修复方案**:
  采用 `serde_json::Value` 逐条解析迭代器，过滤跳过无效记录，并返回成功导入的有效记录数量。
