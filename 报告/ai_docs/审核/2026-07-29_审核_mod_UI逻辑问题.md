## 问题分析

### 现状

当前前端测试 120 项全部通过，Rust 测试 176 项全部通过，TypeScript/Vite 生产构建通过。现有回归测试覆盖了大量输入边界、URL 白名单、脚本生成和存储恢复场景，但对缓存键与请求语义的一致性、事件监听注册时序及设置连续保存场景覆盖不足。

### 根因

1. **缓存命中键过粗，指定版本可能被错误复用**：`mod_UI/src-tauri/src/search.rs:293-324` 仅使用小写包名作为缓存键，并在命中后直接将缓存版本写入结果；未比较 `PackageInput.version` 与缓存版本。用户输入 `pkg 1.0.0` 时，如果缓存中保存的是 `pkg 2.0.0`，任务会跳过联网验证并报告缓存命中，脚本生成阶段可能因此安装错误版本。
2. **依赖缓存未区分来源和版本**：`mod_UI/src-tauri/src/dependency.rs:273-277` 以包名读取依赖缓存，`356-365` 命中后直接使用缓存依赖，`407-415` 新结果仍以包名写回。相同包名在 CRAN、Bioconductor、GitHub 或不同版本之间的 DESCRIPTION 依赖可能不同，切换来源或版本后会复用旧图，导致依赖图和依赖安装建议不准确。
3. **检索事件监听存在启动时序竞态**：`mod_UI/src/useSearch.ts:47-87` 在 `useEffect` 中异步调用两次 `listen`，而 `startSearch` 可在同一组件挂载后的监听注册 Promise 完成前调用 `start_search`。后端会立即发送 `search-log-batch` 和 `search-progress` 事件，早期事件可能丢失；最终响应只能补回有限结果和日志，实时报告可能缺少开始阶段的进度。
4. **设置连续修改时存在保存请求被静默跳过的行为**：`mod_UI/src/useSettings.ts:79-86` 在保存请求进行期间拒绝新的 `persistSettings` 调用，`mod_UI/src/App.tsx:134-141` 的每次设置改变都会立即触发保存。当用户快速连续调整多个设置时，后续变更只更新前端状态，不会排队保存；界面提示“设置操作正在进行，请稍候”，但没有自动重试或再次保存机制，重启应用后可能丢失最后修改。

## 核心发现

1. **高优先级逻辑问题**：搜索结果缓存未校验指定版本，可能直接返回与用户请求版本不一致的结果。
2. **高优先级逻辑问题**：依赖缓存未包含来源、仓库和版本维度，跨来源或版本检索可能生成错误依赖图。
3. **中优先级界面一致性问题**：检索事件监听注册与任务启动没有建立就绪屏障，存在早期日志和结果丢失窗口。
4. **中优先级持久化问题**：设置保存使用拒绝并发而非排队或合并保存，快速连续操作可能造成最后状态未落盘。
5. **验证结果**：未发现当前会导致编译失败的缺陷；前端 120 项测试、Rust 176 项测试和前端生产构建均通过。
6. **未列为安全问题的事项**：上述问题属于结果正确性、时序和持久化一致性，不具备明确攻击路径，按逻辑缺陷处理，不标记为漏洞或安全风险。

## 实施方案
