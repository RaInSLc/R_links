# 搜索量扩展与智能化优化方案

> 生成日期: 2026-07-15 | 类型: 方案 | 状态: 草稿

## 背景

`mod_UI` 当前已经具备多源检索、缓存命中、请求预算、并发控制、失败分类、代理设置和更新链路提示等能力。随着用户一次性搜索包数量增加，搜索流程会从“单包准确性”转向“批量任务调度、失败恢复、可解释性、资源控制和智能决策”的综合问题。本方案围绕“搜索多时还有什么值得优化、逻辑上如何更聪明和更灵活”进行工程化梳理。

## 问题分析

### 现状

当前搜索流程主要由前端 `useSearch.ts` 发起 `start_search`，后端 `search.rs` 负责解析输入、加载缓存、构建 HTTP Client、按固定并发批次检索、通过事件实时返回进度，并在完成后返回结果和依赖图。后端已有 `MAX_CONCURRENT_PACKAGES`、`MAX_SEARCH_HTTP_REQUESTS`、`MAX_SEARCH_DURATION`、缓存可信判断和停止任务能力。前端报告页已能展示结果、日志、失败分类，并支持按失败类别回填重试。

当前架构适合中小批量搜索，但在 100 至 500 包规模、GitHub 限流、网络波动、缓存新旧混合、重复输入、依赖图扩展等场景下，仍存在进一步提升空间。

### 根因

1. 搜索调度仍以固定批次和固定并发为主，未根据来源、失败率、限流状态、缓存命中率和网络耗时动态调整策略。
2. 结果状态已经分类，但前端尚未形成完整的“任务队列视角”，用户难以判断每个包处于待处理、缓存命中、在线检索中、已重试、最终失败等阶段。
3. 缓存策略以命中跳过和可信反馈为主，尚未引入分层缓存、过期策略、来源级可信度和批量预热。
4. 搜索模式仍偏“执行用户输入”，缺少“输入前智能规划”和“执行中自适应调整”。
5. 大批量场景下，报告页渲染、日志增长、依赖图构建、失败重试和历史记录保存都需要更明确的性能边界。

## 核心发现

1. 最值得优先优化的是“搜索计划器”：在真正请求前先将输入拆分为 CRAN、Bioconductor、GitHub、URL、未知包名和可能误输入几类，并给出预计请求量与耗时。
2. 固定并发可以升级为“来源感知并发”：CRAN/Bioconductor 索引请求可批量复用，GitHub API 请求应更保守，并在限流后自动降速或暂停。
3. 缓存应从简单命中扩展为“分层缓存”：强缓存用于近期可信结果，弱缓存用于过期但可先展示的结果，并允许后台验证刷新。
4. 失败重试应从手动回填升级为“重试策略”：超时适合延迟重试，限流适合等待或提示 Token，未找到适合切换全量检索，错误适合换镜像或降低并发。
5. UI 上应增加“批量任务视图”：展示队列进度、来源分布、缓存命中率、限流状态、剩余预计时间和可重试分组。
6. 智能化不应直接替用户隐藏决策，应采用“建议 + 一键应用”的方式，例如建议开启全量检索、配置 GitHub Token、降低并发、按来源拆批搜索。
7. 大批量搜索需要建立性能基准，避免 500 包输入、1000 条日志、10000 条历史和 500 节点依赖图导致前端交互退化。

## 实施方案

### 方案概述

建议按三个阶段推进：第一阶段提升批量搜索可解释性，第二阶段引入自适应调度和缓存策略，第三阶段建设智能搜索计划器和性能基准。每个阶段都应保持现有搜索结果结构兼容，优先增加可选字段和 UI 展示，不一次性重写搜索核心。

### 预期效果

执行后，用户在大量搜索时可以提前知道任务规模和潜在风险；搜索过程中能看到任务状态和失败原因；失败后可以按策略重试，而不是简单重复全部搜索；缓存能在保证可信度的前提下缩短等待时间；GitHub 限流和网络波动场景下可以自动调整，不再完全依赖用户手动判断。

## 最终建议

下一步优先做两个低风险高收益改动：第一，增加搜索计划预览，让用户在开始前看到批量任务规模和建议模式；第二，扩展报告页任务摘要，把缓存命中、失败分类、耗时和重试建议串起来。随后再推进来源感知并发、强弱缓存和自动重试策略。这样可以先提升“聪明程度”和“灵活性”的用户感知，再逐步改造后端调度核心，降低回归风险。
